# Worktree discipline — the parallel-instance rule

> **Supersedes the old "branches, never worktrees" ban** (2026-06-07; the former `branches-not-worktrees.md` redirect has been folded in here and removed). Maya's standing rule.

Multiple agents/instances (Claude, Codex, others) build this app **in parallel**, and git allows only **one branch checked out per folder** — so parallel branches need separate folders, and `git worktree` is the supported, memtrace-aware tool for it. **Worktrees ARE in active use, under discipline:**

1. **Baseline = `main`.** `main` (`== origin/main`) is the single integration branch and the genuinely live one — nothing else is "functionally main." `git fetch` and branch every worktree off the **latest `origin/main`**; keep it rebased so it never drifts behind. After every approved merge, reconciliation, CI repair, or handoff, push local `main` and verify `HEAD == origin/main` with known CI state before starting new feature work.
2. **Reuse before you create; one worktree per active instance.** **Before spawning a new worktree, reuse an existing suitable one** if it's free and on (or rebasable to) fresh `main` — don't pile up near-duplicate folders. Otherwise create exactly one, named `Rebuild-Project-Root.<feature>` on branch `feature/<name>`.
3. **Always register a new worktree as a memtrace overlay — immediately.** `watch_directory(path="<worktree path>", repo_id="Rebuild-Project-Root")` re-parses only touched files (~80 ms save→queryable, respects `.gitignore`) — never full-re-index a worktree. ⚠️ The `repo_id` MUST be the canonical id from `list_indexed_repositories` (`Rebuild-Project-Root`) — a watch registered under a nonexistent repo_id (the old `spinventory-app` wording here caused exactly that, fixed 2026-07-08) feeds the graph nothing and memtrace won't warn you. The canonical graph is indexed **once** from `main`; each worktree rides as a **diff-only overlay**. Query your own scope with `find_code(query=…, worktree="<id>")` (or `include_overlays=[…]`); other worktrees stay invisible to you.
4. **Commit everything as you go.** Never leave uncommitted work stranded in a worktree — it's invisible to memtrace and the easiest thing to lose. **COMMIT BEFORE DISPATCH — never dispatch a worker into a worktree with uncommitted changes; a worker may reset the state it was handed.** Not hypothetical: on 2026-08-17 a dispatched worker ran `git checkout -- .` followed by `git clean -fd` inside another agent's worktree and destroyed uncommitted work (recovered from patches). So, before every dispatch: **make `git status` clean.** Commit real work (a `wip/` branch is enough) and move scratch files out of the worktree — untracked files are exactly what a force-clean takes. The rule covers EVERY dispatch, not only workers you expect to write files: a "read-only" worker still has a shell, and deciding per dispatch which workers are safe is the judgment call this rule exists to remove. **Dispatch cwd = YOUR OWN worktree** (R-codified 2026-08-17 under Maya's same-day every-agent-in-their-own-worktree directive; previously only the SPEC §5 default "workers run INSIDE their orchestrator's existing worktree" plus incident history, not written rule — V's citation challenge exposed the gap): point workers at the dispatching agent's own worktree, or a scratch dir outside any repo for repo-less tasks — never a main checkout, never another agent's worktree. Provenance: the HED-56/64 materialization races arose precisely from several agents dispatching into one shared checkout (observed live 2026-08-15); HED-56's fix made the race survivable, not the practice good — a shared checkout still exposes whatever untracked files sit there to the worker's shell (2026-08-17: five untracked files, two of them other agents', sat in a shared root during a dispatch) and muddles attribution of stray files. A one-off cross-repo need means create/reuse YOUR worktree in that repo first, not borrow the shared root. **And the converse (R-codified 2026-08-17 after doing it wrong): while a dispatch is IN FLIGHT in your worktree, the worktree is the WORKER'S — no branch switches, no stash, no edits until it reports.** R switched branches under a running worker for an unrelated hotfix; the tree happened to be clean and the branches near-identical, so it was luck-not-design again (same lesson as V's shared-root dispatch). Need to work while a worker runs? That's what a second branch in a SECOND worktree, or waiting, is for.
5. **All work MUST land on `main`.** After Maya verifies it, the authoring instance merges its chunk to `main` via the PR flow, **promptly** — nothing stays stranded on a worktree branch.
6. **Leave no trail — remove the worktree when its work lands.** `git worktree remove <dir>` is **lossless** (branch + commits kept; only the folder goes) and the overlay *data* gets swept (`cleanup_worktrees`). **But the watch registration is NOT auto-removed** (memtrace-public [issue #39](https://github.com/syncable-dev/memtrace-public/issues/39)) — it lingers until the next daemon restart, so **immediately after `git worktree remove`, also call `unwatch_directory(path="<worktree path>")`** (Maya-approved addition, 2026-07-08). You end with *branches*, not a pile of folders. (Branches themselves are kept until the app ships — see [[feedback_defer_branch_cleanup]].)

**Retire any existing worktree losslessly:** commit any uncommitted changes to a `wip/<name>` branch first, then `git worktree remove <dir>` (branch + commits kept).

**Why this replaced the ban:** the old ~30-worktree mess was a *discipline* failure — stale worktrees drifted behind `main` with uncommitted work stranded in forgotten folders ("fixed bugs came back"). The fix is the discipline above (off fresh `main`, reuse first, register the overlay, commit, merge promptly, remove when done), not banning the tool that makes parallel instances possible.

**Single app working copy / integration branch:** `Spinventory-Rebuild-Official/Rebuild-Project-Root` (`main`).

## Root-checkout git quiescence (R-codified 2026-09-06, HED-459 — Y's proposal, ratified msg 1403)

Root-checkout git operations (fetch/merge/fast-forward, `worktree add`/`remove`) **QUEUE until no
agent's worker or test suite is running in any worktree of that repo**. A linked worktree shares the
root's `.git`; a root HEAD move or index churn mid-run starves git subprocesses in the worktrees —
5 of 6 known full-suite flake events (30–90s timeouts, all green on quiet re-run) coincided with
exactly this, and it also fires false "worker escaped" warnings on dispatch ledger rows. Post-merge
tails therefore do the REMOTE parts immediately (push, PR state, Linear) and DEFER the local root
refresh until the repo is quiet. Worktree-internal operations in YOUR OWN worktree are unaffected.
